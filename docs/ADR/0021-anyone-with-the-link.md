# ADR 0021 - Anyone with the link: a bounded exception to LAW 2

Date: 2026-08-10 · Status: accepted · Card #612 · Builds on ADR 0017 (sharing a document with a named person), ADR 0019 (cross-partition document sharing), ADR 0020 (conversation-scoped sharing, and where it is enforced)

**Supersedes** the "named grantees who sign in, no bearer links" ruling in `docs/GOAL_ACCEPTANCE.md` (not in the public tree, #685), "Decisions already made":

> **Audience:** named people who sign in. No bearer links (ADR 0017's reasoning binds here too, and harder, since this share carries document access).

That ruling was itself ADR 0017's, taken 2026-08-06:

> If we later want link-sharing for a genuinely public document, it should be a *different* feature with a different name, not a loosening of this one.

This is that different feature.

## Context

ADR 0020 gave a conversation share a recipient who signs in and keeps asking, answered from exactly the documents the thread cited. The owner's decision, taken 2026-08-10, adds a second audience to the same share:

> They dont need to sign in, they just click the link... Just like how chatgpt is done, someone types, and just shares the convo, and the other person can continue. This time, it has access to the main user's DB.

The share modal (design spec `2026-08-10-link-sharing-design.md`, not in the public tree, #685) now offers a SharePoint-style picker between two audiences for the same share: **Specific people**, who sign in and are named by email (ADR 0020, unchanged), or **Anyone with the link**, who need neither. Everything downstream of the picker - which documents are exposed, expiry, revoke, the management surface - is common to both. Only the identity story differs, and identity is exactly what ADR 0017 refused to give up.

`current_user` (`src/dbsearch/server/app.py:356`) is the chokepoint every retrieval route depends on, and its own docstring names the failure it exists to prevent: "an anonymous visitor reaching live customer data or mutating it." "Anyone with the link" is exactly that outcome, deliberately chosen. It is the first time the product answers a question for a caller it cannot identify, and it is a direct, named exception to LAW 2 as written in `SKILL.md`: "never return a result the user is not already authorized to see... the permission filter mandatory and default-deny." A link visitor has no permission filter to be default-deny about, because there is no permission - there is a token.

The ChatGPT comparison the owner used is worth being precise about, because it understates what we are building. A ChatGPT share link freezes a transcript; nothing the visitor types touches ChatGPT's retrieval. This link carries live retrieval against the owner's own documents, on every question a visitor asks, for as long as the link lives. The resemblance is the sign-in-free URL. The exposure is not comparable at all.

## Decision

Possession of an unguessable 128-bit token IS the authorization. This is a deliberate, bounded exception to LAW 2, not a loosening of it: the token-holder is defined as authorized for exactly the share's snapshot, and nothing else in the product treats mere possession of a URL as a credential. LAW 2 still holds everywhere else; this ADR carves out one route family and states in writing what it is allowed to hand over.

### The four bounding properties

These are the invariants (spec s2) that make the exception bounded rather than open-ended. Every part of the mechanism below exists to hold one of these, and any later change to the link feature must keep holding all four.

1. **Scope is the thread's cited documents, snapshotted at share time.** Never the workspace, never a store, never anything the conversation did not already cite.

   **"CITED" MEANS THE EVIDENCE A TURN WAS ANSWERED FROM, NOT ONLY THE DOCUMENTS ITS ANSWER CARRIES A `[n]` MARKER FOR, and this sentence is here because the looser wording misled a reader of this ADR into filing the difference as a defect (#622, 260811).** `Turn.cited_docs` is `QueryResult.retrieved_docs`: the documents that survived the permission trim and the top-k cut, every one of which had its text placed in the prompt as context (`QueryService._context_and_citations`). A share grants exactly that set.

   Narrowing the grant to the marked subset is the obvious-looking improvement and it is **rejected**, for the reason that has already cost this codebase three separate defects (`turns_withheld`, #601's post-share boundary, and the #610 exclusion filter): it would close the GRANT channel while leaving the CONTENT channel open beside it. The recipient reads the answer text, which was synthesized with the unmarked document's content in the prompt and can restate it verbatim; granting only the marked documents would mean handing over content derived from a document the recipient is not authorized to retrieve, with no grant anywhere to show for it - strictly worse for that document's owner than granting it, because nothing records that it travelled. Whether a model "used" a document it was shown is not a fact the system can observe; which documents it was SHOWN is. The invariant is built on the second because only the second is knowable.

   What #622 did fix is the claim made to the READER. The Sources rail listed the whole evidence set under a heading that a user reads as "what this answer used", so an answer citing one document showed two sources - and a refusal, which points at nothing, showed two as well. Every retrieved document is still listed (it is what the answer was produced from), and one the answer carries no marker for is now marked as such rather than presented as a source of the claim.
2. **Read only, and never the bytes.** `download` is 404 for a link visitor, always. Citations expose filenames and the cited passages, nothing more.

   This sentence was written before the code did it, and for the whole of #605 it was false (#612 review, Finding 1): `QueryService._context_and_citations` builds `{doc, title, uri, locator}` and the link routes returned it verbatim, so a visitor was handed the source URI of every cited document - on a SharePoint or Drive deployment, the tenant, the site, the library, the folder path and the filename, rendered as a clickable link with the URL printed underneath (`static/js/ui/components.js`, `sourceCard`). The invariant now holds because `link_access.visitor_citations` narrows a citation to `{doc, title}` at the point the VISITOR's response is assembled - the two ask routes and the transcript - and nowhere else: a signed-in caller's citation is unchanged, because she has an account and the uri is how she opens a source she is already entitled to open. The reason the rule is the audience's and not the citation builder's is that a link is forwardable by construction, so who receives it is not a set the owner chose; a field that is merely over-sharing with a colleague is a disclosure when the reader could be anyone.

   **A RESIDUAL REMAINS, and this paragraph exists because the first version of it claimed otherwise** (#612 re-review, Finding C). It said `doc` is "the opaque external id the frontend keys a card on, never a path". That is true of some connectors and false of at least one: `FolderConnector` sets `external_id = rel.as_posix()` (`src/dbsearch/connectors/folder.py`), documented in `src/dbsearch/core/validation.py` as exactly the shape `"all-staff/handbook.txt"` - a legitimate design (the relative path is the stable key, and multi-segment ids are explicitly allowed for connector-produced ids), but it means that on a FOLDER-BACKED deployment a link visitor is still handed a folder path, through `doc`, after the uri and locator are gone. SharePoint Graph (`item["id"]`) and upload ids are genuinely opaque; the folder connector is the case that is not.

   `doc` is NOT stripped, deliberately: it is the key the visitor surface renders a source card on and the value a `[n]` marker resolves against, so removing it removes the citation rather than narrowing it. So invariant 2 is honestly stated as: the source URI and the locator never reach a visitor, and the remaining exposure is whatever the deployment's connector chose to make its document id - which on a folder deployment is a path, and which the owner has no way to see or change today. Recorded as a known residual, not as a closed gap; the fix, if it is wanted, is a per-share display id rather than anything in this route family.
3. **Bounded in time.** Every link has an expiry. Default 7 days, owner-settable at share time.
4. **Killable.** Revoke is instant and kills every fork at once.

## Mechanism

No new authorization concept is invented. `GrantRegistry.live_principals_for` (`src/dbsearch/api/grants.py:364`) stays the single ACL enforcement point, and a link visitor's grants are ordinary ADR 0020 conv-scoped grants like Alice's - a `conv_id`, a document, a principal. The only new thing is what the principal names: a sentinel `link:<share_id>` instead of a real `grantee_oid`, minted when the share is created and requiring no identity to exist behind it.

`GET /c/{token}` is a new route family that resolves the token, looks up the share it hashes to, and builds a `ReadScope` for that visitor exactly the way `_request_scope` builds one for a signed-in caller - except two things are different on purpose, and both exist to hold invariant 1.

**The partition is synthetic: `linkvisitor:<share_id>`.** It matches no real partition anywhere in the system. This is not incidental - it is the entire reason the mechanism is shaped this way, and the reason traces directly to #601.

`ReadScope.allows` (`src/dbsearch/ports/base.py:173`) is `tenant_id == self.partition or (tenant_id, doc_external_id) in self.doorway` - the partition arm short-circuits TRUE before the doorway is ever consulted. ADR 0020 exists because that short-circuit had already burned this product once: conversation scoping was placed in partition routing, on the reasoning that ADR 0019 already had exactly one place that routes and one place that authorizes, and putting a conversation opinion in the ACL side too would let the two drift. It was wrong, because grantor and grantee sharing a partition is not an edge case - it is every self-host box and every single-organization Entra tenant - and on that shape the doorway is never reached, so a rule expressed only there is never applied. #601 reproduced it end to end: `/search` with no conversation, "Your data", segment previews, and the raw file bytes, all handed to a recipient whose only authorization anywhere was one grant naming one conversation.

A link visitor has no real partition to begin with - there is no signed-in session, so there is nothing for `resolve_tenant` to canonicalize. If this route assigned the visitor the deployment's own home partition (the value every self-host box and every single-org tenant already share), `allows` would return TRUE on the partition arm for every document in the workspace **before the doorway ran**, leaving the ACL overlap as the ONLY remaining refusal between a visitor and that workspace.

**Be precise about that, because an earlier draft of this paragraph was not, and an ADR that misdescribes its own guarantee is worse than one that omits it** (#605 review, Finding 1). It said "before the doorway or the ACL ever ran". The ACL DOES still run: `IndexPort.search` intersects `allowed_principals` on every chunk, unconditionally, and that is ADR 0017 s1's single enforcement point. Reproduced during review: a link visitor given the grantor's real partition still does NOT receive an excluded document over HTTP, because a visitor's principals are the sentinel `link:<share_id>` plus this share's conv-scoped grants, and no other document's ACL names any of them. Removing the ACL-side conversation scoping on its own does not disclose it either - what actually holds the line at HTTP level is that the sentinel is a per-share principal nothing else names.

So the synthetic partition is **defence in depth, and it is kept for that and stated as that**. It is the layer that holds if principal expansion ever widens - an org-audience principal reaching a visitor, a #601-shaped regression on the ACL side, a future identity adapter that resolves an unknown oid to something non-empty - any of which would turn "the ACL happens to name nothing a visitor holds" from a guarantee into a coincidence. `linkvisitor:<share_id>` cannot equal any tenant's real partition, so `allows`'s partition arm can never fire for a visitor, and every document a visitor reaches must come through the doorway AND then through the ACL overlap: two independent refusals, either of which would have to fail on its own, which is the same pair a signed-in grantee's access already depends on. The ACL-side half is the one ADR 0020 put there: `live_principals_for` expands `link:<share_id>` only while its conversation is the one the visitor is asking inside, and drops it otherwise, same as any other conv-scoped grant.

**The token is stored as a SHA-256 hash, never in plaintext.** The database row that resolves `GET /c/{token}` holds the hash; the token itself exists only in the URL the owner sends and in the visitor's browser. A database read, a backup, or a leaked snapshot yields a table of hashes that authorize nothing on their own - recovering a working link from one requires reversing SHA-256 over a 128-bit space, which is the same margin the token's own unguessability already assumes. This is the standard treatment for a bearer credential and there is no reason for this one to be an exception: anyone who can read the `conversation_shares` table (an operator, a support engineer, an attacker with a SQL-injection foothold, a stolen backup) must not thereby acquire the ability to open every live share.

## What is NOT granted

A link visitor never has `current_user` - there is no session, no cookie, no bearer identity `resolve_identity` can produce. Every route that is not part of the `/c/{token}` family depends on `Depends(current_user)`, and `current_user` 401s when there is nothing to resolve. This is why the six-surface probe (GOAL_ACCEPTANCE.md step 7, re-run anonymous) holds for a link visitor without a single line of code written to defend any of those six routes individually: `/search` outside the thread, "Your data", segment previews, `/download`, `/ask/suggestions`, and `/chat` in an unrelated conversation all refuse before any authorization logic runs, because they refuse before any IDENTITY exists to run authorization against.

Name this precisely, because it is a structural property of the route table today, not a property of the link feature, and it is exactly the property that would silently stop holding if a later change gave link visitors a real session or a bearer cookie that `current_user` accepts. The day someone does that - to make `/c/{token}` feel more like a normal signed-in surface, say - every route this ADR currently gets for free reopens, and the six-surface probe becomes load-bearing again in the way it already is for a signed-in grantee under ADR 0020. Nothing about the `linkvisitor:` partition or the `link:` principal would catch that regression, because both only govern what happens once a caller has passed `current_user` - and a visitor with a real session would have passed it.

Within the `/c/{token}` family itself: `download` is 404 always, per invariant 2 - a link visitor is never routed to the bytes endpoint at all, regardless of what the doorway or the ACL would say about the document. `/search` outside the shared thread returns empty with `corpus.authorized_docs: 0`, the same shape a named grantee already gets outside her shared conversation (ADR 0020), because the conv-scoped grant behind `link:<share_id>` only expands while that conversation is active.

## Consequences

**Accepted.**

- **The single-worker constraint ADR 0020 recorded is inherited unchanged, and gets no easier.** `GrantRegistry._by_id` is a per-process cache hydrated once at boot; a revoked link is only as dead as the worker that serves the next request knows it to be. A link is meant to be forwarded further than a named share ever is - that is the whole feature - so a stale worker keeping a revoked link alive is a worse instance of the same broken-revocation defect, not a new one. The deploy constraint in ADR 0020's consequences (no `--workers`, cross-process invalidation required before that changes) governs this feature too.

- **That constraint is now USER-VISIBLE, as a false success on a revocation action** (#607/#608 review round 1, Finding 2). This is not a new defect and nothing here introduces one; what is new is that the owner is now *told* the thing that may not be true. Before #607 the constraint was invisible: revocation happened from a modal inside the conversation, and nobody was shown a durable list of what a share currently opens. `GET /shares/mine` and `PATCH /shares/{share_id}/scope` change that. The PATCH writes through `GrantRegistry.revoke` and `ConversationShareRegistry.set_turn_cutoff`, both of which mutate process-local `_by_id`; every read path (`live_grants_for`, `granted_docs`, `visitor_scope`, `find_by_token`) reads that same process-local map and never re-reads the store. So on a multi-worker box a link visitor pinned to another worker keeps retrieving the removed document until that worker restarts, **while the owner receives a 200 and then sees a narrowed row in her management surface confirming it**. She has been told a revocation action succeeded, and has a durable screen agreeing with her, on a box where it has only succeeded for a fraction of traffic.

  Recorded rather than fixed, deliberately, and the fix is NOT a local one: it is the cross-process invalidation ADR 0020 already names as the precondition for running with `--workers` at all. Until that exists, the deployment constraint IS the mitigation, and this paragraph is here so that the next person weighing "can we scale this box out?" reads a consequence stated in terms of what a user is told, not only in terms of a cache.
- **A per-link question rate cap bounds the cost of a forwarded link**, `DBSEARCH_LINK_QUESTIONS_PER_HOUR`, default 30. A named grantee's cost is bounded by how many people the owner is willing to name; a link has no such ceiling by construction; the cap is the substitute.
- **Every question a visitor asks is logged and readable by the owner** (spec s5), because the owner asked to see what strangers asked. This is a disclosure obligation, not only a feature: a visitor is typing into a page without knowing the owner reads it, so the share page must say so plainly and visibly at the point of asking - not in a footer, not only in a policy document a visitor never opens.
- **The ChatGPT comparison undersells the exposure**, restated as a consequence rather than context: a ChatGPT link's blast radius is a frozen transcript. This link's blast radius is however much of the owner's document corpus the shared thread happened to cite, for as long as the link lives, to anyone it is forwarded to. Invariants 1-4 are the whole of what keeps that bounded; there is no fifth check standing behind them.

**Rejected.**

- *Giving a link visitor a real, if scoped, session.* This is the change flagged above under "What is NOT granted": it would collapse the free 401 every non-`/c/{token}` route currently gets from `current_user`, and every one of those routes would need an explicit, individually-audited guard instead of inheriting one from the chokepoint. `current_user`'s whole value is that a route needs no memory of anonymous callers to be safe from them; a scoped session for visitors throws that away for a convenience nothing in the design asks for.
- *Reusing a real tenant partition for link visitors, home or otherwise.* This is the #601 shape by construction, argued above under Mechanism: the partition arm fires before the doorway is consulted, so the routing half of the refusal simply stops existing and the ACL overlap is left standing alone. Rejected as defence in depth rather than as the sole guarantee - the corrected paragraph above says exactly how much each layer is doing, and the honest reason to keep this one is that it is what holds when the other layer's assumptions change. A visitor scope must have no real partition to equal, which is the entire reason `linkvisitor:<share_id>` is synthetic rather than borrowed.
- *Storing the token in plaintext for simpler lookup.* A hash lookup costs one comparison the token side already has to compute to authenticate the visitor in the first place; plaintext storage buys nothing this feature needs and turns every future database read of `conversation_shares` into a list of live credentials.
