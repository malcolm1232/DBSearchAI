Architecture · Why "inside the query" matters

Filter after retrieval vs. filter inside the search

❌ Way A — bolted on after

hits = search(vec, top_k=5)
ok = [h for h in hits
    if user_can_see(h)]  # app code
  • Top-k starvation: if 4 of 5 nearest are confidential, user gets 1 result — authorized matches got crowded out.
  • One forgotten if = breach. Every endpoint must remember the filter.
  • Data already left the DB into app memory before being discarded.

✅ Way B — property of the query

hits = search(vec, top_k=5,
  where: chunk.acl
    ∩ user.groups ≠ ∅)
  • Always 5 best authorized matches — ranks only among allowed chunks.
  • No bypass path exists — filter is baked into the index call itself.
  • Unauthorized data never leaves the index → LLM can't leak what it never received.
Cost? Each chunk stores its access-list denormalized beside its vector, so the check is an O(1) set-overlap — no JOIN. Azure AI Search does it via an OData filter; Postgres/pgvector via a GIN-indexed && array-overlap.

Architecture · Boundaries & scale

Two planes — and where sharding fits

🔒 Data plane — per customer tenant Documents, embeddings, index, LLM calls, queries, answers. Everything stays here.
📡 Control plane — yours Metadata only: health, counts, token metering. Never doc text or query content. Can be switched off entirely (air-gapped edition).

Isolation by tenant is the data-residency guarantee — there is no shared cross-customer index.

Where's the shard router?

  • Not inside retrieval. The RAG loop stays simple.
  • Today: one index per tenant — no sharding needed yet.
  • Roadmap: a central orchestrator routes a query to the right tenant's data plane — routing by customer, not by vector range.
  • Within a tenant, scale comes from the queues auto-scaling on backpressure, not sharding.

Honest framing for the interview: built vs. designed.

How it's built · The LAWs (1 of 3)

The LAWs, in plain English — data & permissions

LAW 1 — Data residency

Customer document content — text, file bytes, even the embeddings derived from them — never leaves the customer's cloud. Only metadata (counts, health, cost) crosses out.

Why: enterprises won't buy if their confidential docs touch your servers. This is the whole trust pitch.

LAW 2 — Permission-faithful retrieval

No query may ever return, log, cache, or leak a result the user isn't already allowed to see. The filter is mandatory and default-deny — no feature may bypass it.

Why: the differentiator. Default-deny means "if we're not sure you can see it, you can't."

LAW 3 — Isolated, idempotent connectors

Each data source (SharePoint, OneDrive…) is its own module with its own auth, rate-limiting, and crash recovery. One connector failing never corrupts the index or blocks others.

Why: you're pulling from messy real-world systems; one flaky source shouldn't take down the product.

How it's built · The LAWs (2 of 3)

The LAWs — scale & resilience

LAW 4 — Async, queue-driven

Ingest → parse → chunk → embed → index are decoupled stages joined by durable queues. There is no "do it all in one request" path.

Why: built for 10TB and many tenants from day one — not retrofitted later.

LAW 5 — Isolation by construction

One data plane per customer; no shared index across customers, ever. The tenant boundary is enforced at every layer.

Why: a cross-tenant leak would be catastrophic — so the architecture makes it impossible, not just filtered.

LAW 6 — Stateless compute

Parsers, embedders, and API hold no durable state in memory or local disk — state lives in the vector index / blob storage / Postgres.

Why: lets you scale workers out and do zero-downtime deploys — any worker can die and be replaced.

How it's built · The LAWs (3 of 3)

The LAWs — portability & visibility

LAW 7 — Ports & adapters

Every cloud-specific capability (storage, queue, identity, LLM, vector index) sits behind an internal port with a per-cloud adapter. No Azure SDK calls leak into core logic.

Why: Azure today, AWS / GCP / self-host later — with no core rewrite.

LAW 8 — Observability & cost metering

Every stage emits structured events + per-tenant usage/cost counters — metadata only, never content.

Why: answer "is this customer healthy? what did they cost?" without ever looking at their data.

LAW 9 — Pluggable LLM / embedding

Model providers sit behind an interface — Azure OpenAI by default, but a customer can bring their own in-tenant open model with no code change.

Why: the Ollama / Llama self-host path — same code, different model.

Rerank & relevance-floor run after the trim and are subtractive only — they can drop chunks, never add an unauthorized one. The LLM physically never receives a doc Bob can't see, so it can't quote one.

Default-deny Each chunk carries its ACL (opaque OIDs), denormalized at ingest. Empty ACL matches nobody — "unknown = hidden," never "unknown = visible."

The filter, per backend

IndexPort.search(vec, principals, k) — principals is required; no overload omits it.

Azure AI Search (OData)
allowed_principals/any(
  p: search.in(p,'bob,…',','))

pgvector (SQL)
WHERE allowed_principals
  && %s::text[]

in-memory (Python)
if not (acl & principals):
  continue  # full stop

Proven: Alice (on deal-team) sees the confidential doc; Bob, same question, does not — and can't impersonate her via a body field.

Stages connect only through the queue — each consumes one topic, publishes the next. Three different bottlenecks → each scales independently (e.g. 8 parse · 2 embed · 4 index workers).

Durable queue + idempotent stage = crash-safe Worker dies mid-stage → unacked message re-appears → retried. Safe because upsert replaces by chunk_id. Spikes just deepen the queue (backpressure), never collapse.

Messages carry refs, not bytes

store.put("raw/…", bytes)
  → KEY
publish("parse",
  {"document": {…ref}})

# 10MB PDF stays in storage;
# the queue carries a tiny JSON

Small messages = fast queues, cheap retries — and content never leaves the tenant (LAW 1).

Adapters: Azure Service Bus (durable, crash-safe) · in-memory (self-host, single-process). Same stage code.

Designed-not-wired: queue-depth autoscaling is Phase 3+; self-host drains stages in one process.

Deep dive · LAW 5 — Multi-tenant isolation

No shared index, ever — isolation is the deployment shape

🔒 CUSTOMER A — own subscription own Blob · queues · AI Search index · LLM
DataPlaneAgent("acme")
🔒 CUSTOMER B — own subscription own Blob · queues · AI Search index · LLM

▼ metadata only · per-tenant ▼
📡 CONTROL PLANE — your cloud (run once) _metering["acme"] · _metering["globex"] — separate dicts, never aggregated, never content.

There's no shared index anywhere — a cross-tenant leak isn't a bug you can write, there's nothing shared to leak from. One big customer's 10TB crawl runs in their resource group; it can't touch a small one.

Two layers of isolation

① Primary — deployment (structural)

One resource group per tenant, in the customer's own subscription, via IaC. // isolation by construction (Bicep)

② Defense-in-depth — tenant_id everywhere

model:  Document/Chunk.tenant_id
keys:   raw/{tenant}/… chunk/{tenant}/…
index:  (tenant_id, chunk_id)
pg:     tenant_id text NOT NULL
metering: _metering[tenant_id]

Opaque (LAW 1): tenant_id is a key, not a customer name — even billing can't tell who it is.

Proven: 2 tenants → docs disjoint, metering separate; a 3rd runs fully air-gapped while others report.

Deep dive · LAW 6 — Stateless compute

Workers remember nothing — the store remembers everything

⚙️ STATELESS COMPUTE — replaceable, scale-out parse · embed · index workers · the Query API
hold nothing between requests — read input, do work, write out, forget
▲ read by ref  ·  write by ref ▼
💾 DURABLE STATE — managed stores (the source of truth) Object store (Azure Blob) · Vector index (AI Search / pgvector) · Postgres (sessions). The only place state lives.

Any worker can be killed mid-flight and replaced — nothing important was in it. That's what makes scale-out + zero-downtime deploys a knob, not a redesign (ADR 0005).

text = extract(raw)
store.put("text/…", text)  # write
publish(next, {ref})  # forget

Deep dive · LAW 9 — Where the model runs

"Nothing leaves" depends on the endpoint, not magic

Same adapter code in all three — only base_url changes. But the URL is exactly what decides whether your data leaves.

① Self-host open model

You run open weights (Llama/Mistral) on your own box.

base_url =
http://ollama.internal/v1

Data leaves? NO ✅

No provider at all — true air-gap. Prompts hit your machine.

② Vendor's public API

You call the vendor's hosted endpoint directly.

base_url =
https://api.anthropic.com

Data leaves? YES ⚠

The vendor does receive your content. Dev/demo only — code logs a LAW-1 warning.

③ Vendor model, your boundary

Vendor's model deployed inside your cloud tenant.

base_url =
my-co.openai.azure.com

Data leaves? NO ✅

e.g. Azure OpenAI in your subscription — stays in your compliance perimeter. The default.

So "base_url is the seam" = code portability, not data magic. Moving a model in-boundary needs no code change — but you must actually move it in-boundary (① or ③). The raw public API (②) genuinely sends data to the provider. "Nothing leaves" only holds when the model runs somewhere you control.
The takeaway

User need → architectural decision

1. It's RAG — chunk, embed, retrieve, generate.

2. The hard problem was trust: in an enterprise, an answer must respect who is allowed to see what.

3. So we made permission a property of the search itself, and kept all data inside the customer's tenant.

Permission-faithful by construction Cloud-portable (Azure · Postgres · in-tenant LLM) Scales per-stage, isolates per-tenant
